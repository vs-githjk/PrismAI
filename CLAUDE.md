```bash
cd frontend && npm install
npm run dev        # localhost:5173

```

```bash
cd backend
pip install -r requirements.txt
```

## Architecture

PrismAI is a meeting intelligence app with two layers: a React+Vite frontend and a FastAPI backend.

### Request → Analysis Flow

```
User input (paste / upload / record / bot)
  → POST /analyze-stream (SSE)
  → backend runs a LangGraph StateGraph (two-tier parallel execution)
      orchestrator: DETERMINISTIC routing (no LLM) — runs all agents; sentiment + speaker_coach only if 2+ HUMAN speakers
      Tier 1 (parallel): summarizer, decisions, action_items, sentiment, speaker_coach, meeting_classifier
      tier1_barrier: merges Tier 1 results → runs decision_linker (Tier 1.5) → builds context dict
      Tier 2 (parallel, enriched): email_drafter, health_score, calendar_suggester, action_executor, content_analyst
  → each agent node streams its result as it finishes (graph.astream stream_mode="updates")
  → frontend merges results incrementally: setResult(prev => ({ ...prev, ...chunk }))
  → [DONE] event triggers save to Supabase
```

12 agents total (11 graph nodes + decision_linker in the barrier) — all go through `llm_call()` in `backend/agents/utils.py`. **Analysis agents run on `claude-sonnet-5`** (routed via the `_AGENT_MODEL` contextvar set at the Tier 1/Tier 2 dispatch choke points in `analysis_service.py`, env `PRISM_AGENT_MODEL`); `llm_call`'s bare `PRIMARY_MODEL` default stays Claude Haiku 4.5 (`claude-haiku-4-5-20251001`) for RAG + memory. All fall back to OpenAI `gpt-4o-mini` on error/overload. Never bypass `llm_call`. (Groq was fully removed Jun 2026 — any lingering `groq`/`llama-3.3` mention in older docs or a `_GROQ_SEM`-style variable name is historical.) **Routing is deterministic (Jun 2026): the orchestrator is no longer an LLM call** — `agents/orchestrator.run_orchestrator()` is pure logic that runs every agent, gating `sentiment` AND `speaker_coach` to meetings with **2+ HUMAN speakers** (`count_human_speakers`, Aug 2026 — the bot's own lines under Prism/persona names are NOT a participant; the old any-speaker gate let sentiment grade human+bot dialogues as team dynamics, producing "Prism dominates 81% of talk" verdicts about the product itself, and coach told solo users they "spoke 96%"). The sentiment prompt allows an honest `neutral` and reserves `draining` for genuinely energy-sapping dynamics — an unstructured test/debug session that found what it was hunting is `exploratory`, not `draining`; `calendar_suggester` always runs and self-decides `recommended` (so `CalendarCard` only renders when `recommended`). Tier 2 agents receive a `context` dict built from Tier 1 results: `{summary, decisions, action_items, sentiment, unactioned_decisions, owner_name, meeting_type, human_speakers, word_count}`. **health_score is calibrated (Aug 2026)**: EVERY recording gets a score, graded against what IT tried to be — real meetings against their own goal (casual check-ins that served their purpose land 55–75; <35 reserved for genuine dysfunction), **solo bot sessions graded as INTERACTIONS** (clear ask + useful answer = 55–75; unfulfilled ask = 35–55; fragments/connection tests = 40–55 — never 0 for brevity, never "failed board meeting" verdicts). Badges may be `[]` (observations, not a quota — "Ran Overtime" is banned without duration evidence). The FAILURE fallback is `score: null`, never a fake 50 (a crashed analysis used to render as a real "Fair" meeting for months); the frontend renders null safely everywhere (`overallHealth` checks null BEFORE `Number()` coercion — `Number(null)` is 0; MeetingView shows the health triangle in an "ungraded" wireframe state, `MeetingHealthTriangle ungraded` prop, so the page keeps its visual anchor without inventing a number). Current agent output shapes (post Jun 2026 review): summarizer adds `tldr` + `topics`; decisions add `rationale` (importance surfaced + sorted in UI); action_items add a resolved `due_date` (overdue/due-soon badges); sentiment `tension_moments` are `{moment, status: resolved|carried_over}`; health_score adds `improvement_tip`; calendar_suggestion adds `suggested_time` + `agenda` + `attendees` + `resolved_time` (with an Add-to-Calendar action); `decision_links` maps decisions↔action items.

### Backend Structure

`main.py` is purely wiring — middleware and router registration only. Logic lives in `*_routes.py` and `*_service.py` files. `auth.py` exports a single FastAPI `Depends`: `require_user_id(request)` — it validates the Bearer token against Supabase and returns `user_id`. All auth-gated endpoints use it; `/analyze`, `/chat`, `/agent` are intentionally unauthenticated for the pre-login demo flow.

`analysis_service.py` is the agent registry and LangGraph orchestrator. Key exports: `AGENT_MAP`, `AGENT_RESULT_KEY`, `DEFAULT_RESULT`, `TIER1_AGENTS`, `TIER2_AGENTS`, `_GRAPH` (compiled StateGraph singleton), `run_full_analysis`. The two-tier graph: orchestrator node → Tier 1 fan-out (Send) → tier1_barrier (builds context) → Tier 2 fan-out (Send, enriched with context) → END. Adding an agent requires updating `AGENT_MAP`, `TIER1_AGENTS` or `TIER2_AGENTS`, `AGENT_RESULT_KEY`, `DEFAULT_RESULT`, `_state_to_result`, the graph construction in `_build_graph`, and the agent file itself. If it's a Tier 2 agent, also add `context: dict = {}` to its `run()` signature.

`decision_linker` is a special "Tier 1.5" agent: it runs INSIDE `_tier1_barrier` (not as a graph node, so it's not in `TIER2_AGENTS`/`_build_graph`) because it needs both Tier 1 outputs (decisions + action_items) AND must feed Tier 2 (it adds `unactioned_decisions` to the context that `calendar_suggester` reads). It maps decisions→action items by their original-array index, returns `decision_links` (wired in `AGENT_RESULT_KEY` + `DEFAULT_RESULT` + `_state_to_result`), and `analysis_routes` has a dedicated `tier1_barrier` branch in the SSE loop to stream its output (barrier updates are otherwise skipped). Frontend renders bidirectional links in `MeetingView` (decisions show ↳ linked actions or a "No action item" flag; actions show "From decision: …").

`workspace_routes.py` handles all workspace and invite logic: create/rename/delete workspaces, add/remove members, generate/validate/accept invite tokens (multi-use, revocable by owner). Also exposes `GET /workspaces/{id}/brief` — returns up to 10 open (unchecked) action items from the workspace's meetings in the last 30 days, each carrying `meeting_id` for click-through. Membership-gated. Dedups fan-out copies by `date[:16]` preferring the caller's own row so the linked `meeting_id` opens in their dashboard.

**Per-workspace integrations (#2, Jul 2026):** an admin (workspace `owner` role) connects Jira/Linear/Slack/Teams/Notion once per workspace, and every action in that workspace's meetings routes there — with a **personal fallback** when the workspace hasn't configured that provider. Core is `backend/workspace_integrations.py` → **`resolve_tool_settings(personal, user_id, workspace_id)`**: overlays a workspace's config on top of the acting user's personal settings, **per-provider all-or-nothing** (required fields must all be present; optional fields absent from the workspace config are CLEARED — never field-mix a workspace `jira_base_url` with a personal token), **OAuth (`google_*`/`ms_*`) never overlaid** (personal only in v1), **membership-checked** (fail-closed), gated by `PRISM_WORKSPACE_INTEGRATIONS` (default ON). Reads via the service-role `auth.supabase` (bypasses the table's RLS — the config holds secrets, server-side only). Backward-compatible: zero rows / flag off / no workspace → personal unchanged. Owner CRUD lives in `workspace_routes`: `GET /workspaces/{id}/integrations` (member-gated; per-provider status + a **MASKED** label via `_integration_label`, never raw secrets; `can_edit`=owner), `PUT /{provider}` (owner-only upsert, only known fields persisted), `DELETE /{provider}`. The resolver is wired into `actions_routes` (resolves the meeting's `workspace_id` via `meeting_id`) and `chat_routes` (`/chat` reads the `x-active-workspace` header; the pending-tool entry carries `workspace_id` so a **confirmed** tool routes to the same workspace; `/chat/global` stays personal). Export is server-resolved (decision A): member-gated `POST /workspaces/{id}/export/{slack|teams|notion}` in `export_routes` resolves the workspace webhook/token server-side (secret never reaches the browser; body-cred `/export/*` refactored into reusable `_do_*` helpers), 404 when the workspace hasn't configured that provider. Frontend: `IntegrationsModal.jsx` has a **Personal | Workspace scope switcher** — owner sees editable fields + Save/Disconnect + Test-connection (Test-send stays personal — it validates the tab's own creds); members see a masked read-only status ("Configured by the workspace · label"); OAuth tabs stay personal; the personal path is byte-for-byte unchanged. **Export call sites are workspace-routed (Jul 2026):** `App.jsx` centralizes recap delivery in **`sendRecap(provider, title, result)`** — in a workspace scope it POSTs the cred-less body to `/workspaces/{id}/export/{provider}` first, and ONLY on a 404 falls back to the personal `/export/{provider}` (with `_personalExportBody` carrying the creds); Personal scope goes straight to personal. Used by `exportToSlack`/`exportToNotion` (manual) + `deliverMeetingRecap` (auto-send, still gated on the personal `auto_send_*` flags). `SuggestedActions` Teams action does the same try-workspace-then-personal (its other actions already route via the workspace-resolved `/actions/execute` tool path). Ticket-filing already routes via the tool path. **Still open (deferred):** the live-bot tool path (`realtime_routes._get_settings_for_bot`) is NOT yet workspace-routed (that file is a separate active workstream). Plan + decisions: `docs/plans/2026-07-15-per-workspace-integrations.md`.

`recall_routes.py` now checks for workspace dedup before joining: `_find_shared_workspace_bot()` queries `meeting_bots` to detect if a teammate's bot is already in the meeting. If found, returns `{skip: true, existing_bot_id, owner_user_email}` (email sourced from `workspace_members`) without calling Recall.ai. Registers new bots in `meeting_bots` after a successful join. `_mb_update_status()` keeps `meeting_bots.status` in sync with webhook events. **Idempotency (Jun 2026):** `_process_bot_transcript` is guarded by an in-memory `_processing_bots` set so only ONE analysis runs per bot — `/bot-status` polls used to re-spawn a full analysis on every poll while `status=="processing"` (it couldn't tell a running task from a dead one), piling up dozens of concurrent runs and exhausting Groq's daily token limit. The `/bot-status` call-ended branch is now one rule: run once unless already done/error or in flight (the empty in-memory guard after a restart still allows the legitimate recovery re-trigger).

**Transcription grounding (Jun 2026):** the bot transcribes with Deepgram `nova-3` streaming (`_recall_bot_create_json`), and accuracy on names/jargon is improved two ways. **Lever A — keyterm prompting:** `_gather_keyterms(user_id, workspace_id)` builds a bounded (~40-term, ≤50 clamp) proper-noun list from (source 0, highest priority) the **`custom_keyterms` glossary** (hand-corrected mishearings fed by `correct_meeting_text` — added FIRST so a user's own corrections always survive the cap), teammate names (derived from `workspace_members.user_email` via `_name_from_email`), knowledge-doc titles + mined content proper-nouns, and recent-meeting speaker/owner names (from `meetings.result` — `sentiment.speakers[].name` + `action_items[].owner`), filters generic words (`_KEYTERM_STOPWORDS`), and passes it as Deepgram's `keyterm` param (nova-3-only) on bot create — so spelling is biased toward *your* vocabulary at transcribe time. Best-effort: returns `[]` (config unchanged) on any failure. Wired into both `join_meeting` and `schedule_standin_bot`. **Lever B — async re-transcription:** for **bot-silent** meetings (where the durable transcript is Recall's audio, not the bot-inclusive live buffer), `_process_bot_transcript` calls `_request_async_transcript(bot_id)` → Recall's `POST /recording/{id}/create_transcript/` with `deepgram_async` nova-3 + the same keyterms (batch transcription is materially more accurate than streaming), then `_fetch_transcript(..., prefer_async=True)` holds out for the async download (skips the streaming `/transcript/` fallback until the last attempt) so the better transcript is what gets analysed/displayed/RAG'd. Skipped when the bot spoke (must keep the live transcript with the bot's chat replies → a second transcription would be wasted spend). Flag `PRISM_ASYNC_TRANSCRIPT` (default ON); any failure/timeout falls back to the streaming path. One extra transcription cost, scoped to bot-silent (group) meetings only.

`storage_routes.py` `POST /meetings` accepts an optional `recorded_by_user_id` on the entry — set by the frontend when the user's bot was workspace-dedup'd to a teammate's, so the actual recorder is attributed correctly. `_fan_out_to_workspace()` uses `entry.recorded_by_user_id or user_id` so all fan-out copies share the same recorder regardless of which workspace member's frontend triggered the POST. `/meetings` and `/insights` both accept `?workspace_id=` — workspace mode fetches ALL members' rows (no user_id filter) then deduplicates in Python by `date[:16]` only (within one workspace, two rows at the same minute are the same logical meeting). Prefer the current user's own copy. `user_id` is included in the select for dedup, then stripped before the response. `GET /meetings/{id}` returns a single meeting with workspace-membership auth — used by the upcoming-meeting Brief panel to open source meetings outside the currently-loaded workspace history. **`POST /integrations/test` (Jul 2026, auth-gated):** validates ticket-integration creds before they're relied on mid-meeting — `provider: jira|linear` + the (possibly just-typed, unsaved) creds → `tools/jira.jira_validate` (GET `/myself` + default-project check) / `tools/linear.linear_validate` (GraphQL `viewer`), read-only, returns `{ok, account_name?, project_ok?, error?}`. Surfaces a bad token/project in the Integrations UI ("Test connection" buttons on the Jira + Linear tabs) instead of a silent filing failure later (the Cluster B "Jira connected but nothing happens" class).

All agents import `strip_fences` from `backend/agents/utils.py`. Never redefine it.

`realtime_routes.py` is the live-meeting surface: receives Recall.ai transcript + chat webhooks, runs the utterance accumulator → command detection → tool execution → optional TTS response loop. Also exposes the live-share index (token gated by `bot_sessions.live_token`) and the realtime SSE for the dashboard's live view. This file is large by design — much of the live-meeting product surface lives here. Voice commands get an instant pre-synthesized acknowledgment ("Let me pull up your calendar—") if real audio hasn't started within ~1.2s (`PRISM_ACK`, `PRISM_ACK_DELAY_S`; category taxonomy in `ack_phrases.py`, audio cache in `ack_audio.py` filled at warmup, race timer armed/cancelled in `_process_command`).

**Bot turns in the transcript (Jun 2026):** the bot's own replies are recorded into the saved transcript so a meeting reads as a real dialogue (critical for solo meetings — otherwise it looks like the user talking to themselves) and there's a lasting record of what the bot said. `realtime_routes._record_bot_line(bot_id, state, text, bot_name)` appends `"{persona_name}: {reply}"` to BOTH the live-memory `transcript_buffer` AND the durable append-only `realtime_transcript_lines` (via `_append_realtime_line` + throttled persist), in chronological order interleaved with the human utterances. Called at the two reply-finalization points in `_process_command` (main path + Haiku fallback), replacing the old hardcoded `"Prism: {reply}"` buffer append. In `recall_routes._process_bot_transcript`, when the bot actually spoke (`_BOT_NAME_PREFIXES` — every persona name + Prism/PrismAI — detected in `realtime_transcript_lines`), that bot-inclusive live transcript is used as the final transcript for analysis + display (Recall's audio transcript wouldn't contain the bot's chat replies). Recall `segments` are still used for the recording player. When the bot was silent, behavior is unchanged (Recall transcript primary, realtime fallback when empty).

`ambient_loop.py` is the ambient contribution lane (Automatic mode): content-based triggers (unanswered question / KB hit / blocker) → one grounded 70B call that drafts and prices a contribution → tiered delivery (chat ≥5, direct voice ≥8) behind a speak-time timing gate with a yield rule. Gated by `PRISM_AUTONOMOUS` (+ `PRISM_AUTONOMOUS_SHADOW` for log-only, `PRISM_AMBIENT_VOICE=0` for chat-only). Utterance mode is byte-identical to the pre-lane bot. Spec: `docs/superpowers/specs/2026-06-11-ambient-contribution-lane-design.md`.

**Private live catch-up — "Ask Prism, just you" (Jun 2026):** any meeting participant can privately ask the live bot to catch them up or answer a question, streamed back to their own browser only — never spoken or posted into the meeting. Endpoint `POST /live/{live_token}/ask` (in `recall_routes`, next to `GET /live/{token}`) is **token-gated, no login** (inherits the live-share possession model — it only summarizes data the live page already exposes). Resolves `live_token → bot_id`, rate-limits per token (`realtime_routes._catchup_rate_ok` — 1.5s min interval, 12/min), and streams SSE (`StreamingResponse`, `data: {json}\n\n`, mirrors `/analyze-stream`) from `realtime_routes.stream_catchup_answer(bot_id, mode, question, member_user_id)`. Modes: `catchup` (summarize so far) | `qa`. Context = `meeting_memory.get_memory_snapshot` (rolling summary + live_decisions + live_action_items) + last 30 transcript lines; model gpt-4o-mini. **Knowledge-base fallback is members-only:** a valid Bearer JWT whose user is a member of the bot's workspace (checked in the endpoint) sets `member_user_id`, which unlocks a `search_knowledge` fallback for `qa` (anonymous link-holders stay meeting-only so workspace docs aren't exposed to external guests); the final SSE event carries `sources`. Frontend: shared `components/LiveCatchup.jsx` (streaming thread + "Catch me up" button), mounted on the live-share page (`LiveMeetingView`, primary) and the dashboard live area (`NewMeetingPanel`, when `botStatus==='recording'`). The `/join-meeting` dedup skip responses now include the shared bot's `live_token` (`_live_token_for_bot`) so a dedup'd teammate gets the live view + catch-up from their own dashboard. Spec: `docs/specs/2026-06-17-proxy-representation.md` (Feature B; Feature A "Stand-in async proxy" is planned there, not yet built).

**Solo free-flow (Jun 2026):** when exactly one human is in the meeting, the bot drops the wake-word requirement and treats every substantive utterance as a command (natural 1-on-1 conversation). Driven by Recall `participant_events.join`/`.leave` webhooks (now subscribed in `recall_routes._join` alongside `transcript.data` + `chat_message`) → `state["participants"]` roster → `_human_participant_count` (the bot self-excludes via `_looks_like_bot_participant`, matching `is_current_user`/`is_bot` flags or any name in `PERSONA_NAMES`/`Prism*`). `_solo_mode_active` returns True when humans == 1. Fallback when participant events are unavailable (e.g. mid-meeting restart): distinct human speaker count (`human_speaker_ids`), guarded by `max_humans_seen` so a group meeting never drops into free-flow. Wired in `_dispatch_slow_path_command` (adds the no-wake-word command path, filtered by `_solo_freeflow_eligible`: ≥3 words, not a mute phrase) and `_ambient_on_utterance` (returns early in solo mode so ambient doesn't double-process). Flag: `PRISM_SOLO_FREEFLOW` (default ON). Mute kill-switch + gap-before-speaking still apply.

`chat_routes.py` exposes three chat surfaces in priority order matched by `ChatPanel.jsx`: `POST /chat` (per-meeting chat against transcript), `POST /chat/global` (auth-gated cross-meeting chat), `POST /agent` (intent → tool call). All three call OpenAI `gpt-4o-mini` directly (not via `llm_call`) because they handle their own streaming + history shaping. **RAG trust layer (Jun 2026):** when the tool-calling loop (`/chat` + `/chat/global`) runs `knowledge_lookup`, `build_rag_context()` normalizes the result into a whitelisted `rag_context` (top 5 sources: doc_name, source_type, score, 500-char snippet, page/timestamp/meeting_title + a `has_conflict` flag) returned alongside `reply`. `ChatPanel` renders a conflict banner + Sources cards from this structured data — citations come from `rag_context`, never from the model's prose. (`knowledge_lookup` now also returns `doc_id`/`chunk_id`/`possible_conflict`/`has_conflict` so this works.) `POST /agent` re-runs a single agent; for Tier-2 agents it rebuilds the pipeline `context` from the `result` shipped by `ChatPanel` so re-runs aren't context-blind (e.g. `health_score` sees sentiment's tension resolution). **Continuous per-meeting chat (Jun 2026):** `POST /chat-sessions/{id}` upserts in place when given `session_id` (else inserts + prunes to 3). `ChatPanel` restores the meeting's latest session on mount, auto-saves each turn (debounced, chained so no duplicate inserts), flushes on unmount, and has a "New chat" button that clears the thread + starts a fresh session; `DashboardPage` clears stale sessions on meeting switch (ChatPanel is keyed by meetingId). **Image analysis (Jul 2026):** `/chat` + `/chat/global` accept `image_urls: list[str]`; `_build_user_turn()` switches the user turn to OpenAI vision format (`content: [{type:text},{type:image_url}…]`, capped 3) when images are present — gpt-4o-mini is already vision-capable, no new model. `POST /chat/upload-image` (auth) validates png/jpg/webp ≤5MB and stores to the private **`chat-images`** Supabase bucket at `{user_id}/{uuid}.{ext}` via `auth.supabase` (service-role) → returns `{path, url}` (signed 1h); `POST /chat/sign` re-mints signed URLs from stored paths (own-paths only). `ChatPanel` adds attach button + Cmd-V paste + drag-drop, stages thumbnails (`pendingImages`), renders images inline in the user bubble with a click-to-open lightbox, ships `image_urls` on send, and re-signs stored paths (`resignImages`) on session restore. With images attached, the deterministic rename/agent intents are skipped (they don't handle images) → routes to `/chat` or `/chat/global`. The image **path** is persisted in `chat_sessions.messages` (no migration). Bucket must be created manually in Supabase (private, 5MB, image MIME types) — no RLS needed (all access is server-side + signed URLs). **Part B — live-bot chat images (Jul 2026):** `realtime_routes` captures images shared in the meeting chat so the bot can *see* them. `_extract_image_urls` pulls image URLs from incoming chat text (confident path — Recall relays chat text); the `chat_message` webhook also scans an `attachments` array best-effort (Teams file uploads — logged so the real shape can be verified live). Captured URLs are stashed on bot state (`_remember_chat_images`, last 3, timestamped) and `_fresh_image_urls` (≤5 min) feeds them into `_build_command_messages(image_urls=…)`, which emits the same OpenAI vision content for the live command LLM (gpt-4o-mini). Deferred: live-bot **screen-share** vision (real-time video frames — needs a Recall feasibility spike).

**Meeting text correction (Jul 2026):** `tools/meeting_edit.py` registers **`correct_meeting_text(find, replace)`** — the only tool that EDITS a saved meeting (the rest create external things). It case-insensitively replaces a phrase across the meeting's `title` + `result` JSON + raw `transcript`, persists (caller's own copy, `eq user_id`), and upserts the corrected term into `custom_keyterms` (the glossary that grounds future transcription — closes the loop). Fixes the class where "change MD Academy to FDE Academy" used to fall through to the LLM and get turned into Linear tickets. Gated by `requires="_meeting_id"` (a settings key injected ONLY on authenticated per-meeting `/chat` — so it's invisible to the live bot and `/chat/global`, which have no single meeting to edit) and `confirm=False`. `chat_routes`: `ChatRequest.meeting_id` → injects `_meeting_id`; the tool-loop bubbles a `meeting_updated` flag; on it, `/chat` re-reads the meeting OUTSIDE the LLM loop (so the transcript never bloats model context) and returns `updated={result, transcript}`. Frontend: `ChatPanel` ships `meeting_id`, and on `meeting_updated` calls `onCorrectApplied(updated)` → `DashboardPage.onCorrectApplied` updates result + transcript + history in place (no re-persist; server is already source of truth). Known limits: corrects the caller's own copy only (workspace fan-out copies aren't touched — but the glossary fixes everyone's future meetings); RAG re-indexing of the corrected transcript is not done. The legacy client-only `detectRenameIntent`/`deepRename` in `ChatPanel` (instant single-word card rename, doesn't touch transcript) is unchanged.

`actions_routes.py` is the **Suggested Actions** execution surface (Jun 2026). The Tier-2 `action_executor` agent (in `analysis_service` registry — see below) classifies the meeting OWNER's own open action items into ready-to-run actions (`result.suggested_actions: [{task, owner, owned, action_type: email|calendar|task|chat, title, body, recipients, when, confidence, rationale}]`) — it only PREPARES drafts, never sends. `POST /actions/execute` runs ONE user-approved action: it allowlists resource-creating tools only (`gmail_send`, `calendar_create_event`, `jira_create_issue`, `linear_create_issue`, `slack_post_message` — never read/search/knowledge tools), loads the caller's `user_settings` + injects `user_id`, calls `confirm_and_execute` (the UI already did the approving), and logs an `action_refs` row. Frontend: `components/dashboard/SuggestedActions.jsx` (card + a single adaptive, **approve-first** modal — portaled to body since the dashboard's transformed ancestor breaks `position:fixed`) resolves each `action_type` → a concrete tool based on what's connected (`actionConnections` built in `DashboardPage` from `props.calendarConnected` for Gmail/Calendar + `integrations.{jira_api_token,linear_api_key,slack_bot_token,teams_webhook}`); task→Jira-or-Linear, chat→Slack-or-`/export/teams`. Emails/attendees are filled from the same `suggestedEmails` chips as the follow-up cards. Mounted in `MeetingView` (non-readOnly, only when `suggested_actions.length`).

`calendar_routes.py` owns the Google Calendar OAuth callback exchange, `GET /calendar/events` (lists next-N upcoming events with `attendee_emails` for workspace matching), `POST /calendar/create-event` (the follow-up "Add to Calendar" action — reuses `get_valid_token` for a fresh token + `tools/calendar.calendar_create_event` to insert; adds a Meet link when attendees are present), and the per-meeting bot auto-join settings. `calendar_resolution.py` is pure logic for parsing natural-language date/time references ("next Tuesday at 3pm") — now also extracts time-of-day + more phrasings (end of week/month, numeric M/D) with a `dateparser` fallback; used by both calendar_suggester and action_items (to resolve `due_date`). It returns all-empty for vague phrases ("next meeting"); so when `calendar_suggester` recommends a follow-up the meeting set no concrete time for, it fills a sensible future default (`_default_followup_slot` — next business day @ 10:00) so the card shows a real, editable date instead of nothing (and Add-to-Calendar no longer falls back to "now"). The card is an editable suggestion — nothing auto-schedules. The frontend mirrors it in `lib/resolveDate.js` (client fallback for seed/old meetings) and `lib/dueStatus.js` (overdue/due-soon). `CalendarCard` uses custom `DatePopover`/`TimePopover` (Radix popover) instead of native inputs, with teammate-email suggestion chips.

Dashboard visual invariants (added Aug 2026 after a UI audit — don't regress these):
- **One health colour scale**, `HEALTH_BANDS` / `scoreBand` / `healthColor` in `frontend/src/lib/insights.js` — **five** bands: ≥80 emerald "Healthy", 60–79 lime "Good", 40–59 amber "Fair", 20–39 orange "Weak", <20 rose "Needs work", null/missing → slate "No score". Five, not three, because real scores cluster low (one audited account: 32 meetings, median 20, **max 50** — nothing above 59), so a 3-band scale painted every percentage the same red and differentiated nothing. Colour must stay **directional** (redder = worse) and cyan must never appear in it; both are unit-tested. (Aug 2026: that clustering WAS the `health_score` agent grading bot-command sessions as failed meetings — the agent is now calibrated: everything is graded against its own purpose, solo bot sessions as interactions. Post-calibration one real account spreads 30–75, median 45; keep the five bands.) Importers: `MeetingHealthTriangle`, `MeetingView`, `CalendarView`, `HealthScoreCard`, `MetricTile`, `StatsCanvas`. **Never redeclare a local traffic light** — five competing scales existed at one point, so the same score rendered green on the meeting page, violet on Home, and "Good" on the live card. `ContentAnalysisCard` keeps its own 4-band scale deliberately: it grades content quality, not meeting health.
- **Missing ≠ bad.** `Number(null)` is `0` and `0` is finite, so a `Number.isFinite` guard alone lets a missing value fall through to the worst band / a confident `0`. Check `null`/`undefined`/`''` BEFORE coercing. This shipped three times (MetricTile printing "0 %", `scoreBand` painting unscored meetings red, `healthBucket` calling them "strained").
- **A metric's label is a claim — verify the computation before writing the definition.** Trend's "Delta vs prior" subtracted the *oldest* meeting in the window, and "30-day average" had no window; both were only caught once plain-English hints made them falsifiable. `avgScoreCount` exists so the average can state its sample size. Metric logic is unit-tested on both sides — `frontend/tests/insights.test.mjs` (`npm test`, Node's built-in runner, no framework) and `backend/tests/test_cross_meeting_metrics.py`. **`normalizeInsights` prefers the SERVER's `avg_score`/`score_delta` over the client fallback, so any change to one must be mirrored in `cross_meeting_service.derive_cross_meeting_insights`** or the bug stays live in production. Screenshots cannot catch a wrong number — it renders perfectly.
- **Cyan is for interactive/selected state only** — never for a score band, a status stripe, or a progress bar. A mediocre score used to get the brand accent.
- Figures inherit `tabular-nums` from `.dashboard-page`; don't override it on figure-heavy components.
- Colour a verdict from the TRUE value, never from an animating count-up (that shipped a red "needs work" flash on a healthy meeting).
- A bar/gauge only when the value is genuinely a proportion of something (`MetricTile` gates this behind `bar`); a count next to a bar of itself is decoration.
- `null`/missing data renders a dash, never a confident `0` (`Number(null)` is 0 and finite — check the value, not just `isFinite`).
- **Due badges are anchored and expire (Aug 2026).** `dueInfo(item, reference)` resolves free-text phrases ("tomorrow") against the MEETING date passed as `reference` — never today's date, which made "tomorrow" from a June meeting read DUE TOMORROW forever. A deadline more than 14 days past becomes status `'stale'`: quiet "Was due Jun 14" text, no red badge, and it does NOT rank as live urgency in `byUrgency`/`compareDue`. Backend-resolved `due_date` always wins over the phrase. Tests: `frontend/tests/dueStatus.test.mjs`.
- **Date grouping is one ladder** — `meetingBucket` in `frontend/src/lib/dateGroups.js` (Today · Yesterday · This week (ISO, Mon-start) · This month · Last month · Last 6 months · This year · Older · No date), used by BOTH the Action items page and the sidebar's meeting groups. ## Deployment

- **Frontend:** Vercel auto-deploys `frontend/` on push to `main`. Build: `npm run build`, output: `dist`.
- **Backend:** Render auto-deploys from `render.yaml` on push to `main`. Service name is `meeting-copilot-api` (URL is locked to creation-time name regardless of dashboard display name).

All Supabase migrations live in `supabase/`. Two ways to apply them:

- **Runner (preferred):** `python supabase/migrate.py` applies every migration in dependency order. Requires `DATABASE_URL` in `backend/.env` (Supabase connection pooler URL). All migrations are idempotent (`IF NOT EXISTS` guards), safe to re-run.
- **SQL editor (fallback):** paste files into the Supabase SQL Editor in the order listed below. `full_schema_fix.sql` is a consolidated idempotent script that covers calendar + tools + bot_commands in one shot if you'd rather not run them individually.

Migration order (dependency-correct):

1. `auth_migration.sql` — meetings + chats tables.
2. `calendar_migration.sql` — `user_settings` table.
3. `tools_migration.sql` — `linear_api_key` / `slack_bot_token` columns + `bot_sessions` table.
4. `bot_sessions_live_token_migration.sql` — `bot_sessions.live_token` (unique) so the live-share index survives Render restarts.
5. `bot_commands_migration.sql` — `append_bot_command()` RPC for atomic command appends (avoids read-modify-write race on `bot_sessions.commands`).
6. `memory_migration.sql` — `bot_sessions.memory_summary` (TEXT) + `bot_sessions.live_state` (JSONB) for the three-layer live-meeting memory system.
7. `chat_sessions_migration.sql` — per-meeting ephemeral `chat_sessions` table (replaces single-row `chats` model; backend prunes to 3 most recent per meeting).
8. `chats_unique_migration.sql` — unique constraint on `chats(meeting_id, user_id)` so legacy upsert paths stop racing. Deduplicates existing rows first.
9. `action_refs_migration.sql` — `action_refs` table tracking action items resolved into external tools (Linear/Slack/Gmail).
10. `workspace_migration.sql` — `workspaces` + `workspace_members` (note: `user_id` / `workspace_id` stored as `text`, not uuid) + `meeting_bots` + adds `workspace_id` / `recorded_by_user_id` / `email_claimed_by` columns to `meetings`.

NOT in `schema.sql` — run manually. Idempotent.
25. `custom_keyterms_migration.sql` — `custom_keyterms(user_id text, workspace_id text default '', term text, unique(user_id, workspace_id, term))` — a per-user/workspace **glossary** grounding Deepgram nova-3 transcription. NOT in `schema.sql` — run manually. Idempotent.

**Stand-in async proxy (Feature A, Jun 2026) — `proxy_routes.py`:** a workspace member who can't attend has Prism represent them. **A1 (composer):** "Can't make it" on an upcoming meeting (≥10 min out) opens a chat (`StandInComposer.jsx`, rendered at DashboardPage level — NOT inside the New Meeting `DropdownMenu`, since a portaled modal there gets torn down on the dropdown's outside-click). `POST /proxy/representations` drafts from the user's action items (fuzzy `owner` name-match across their last 30 days) + their `proxy_profiles`; `/{id}/message` refines (conversation persisted to `messages` so reopening resumes, not regenerates); `/{id}/approve` freezes `approved_body`. **A2 (scheduled join):** on approve, `recall_routes.schedule_standin_bot()` creates a **scheduled Recall bot** (`join_at` = meeting start; shared payload `_recall_bot_create_json`, also used by `join_meeting`) owned by the user, registered in `meeting_bots` with status `scheduled`. Dedup (`_find_existing_bot_for_standin`, includes `scheduled` status) attaches to a teammate's/own existing bot instead of double-booking. Cancel (`cancel_standin_bot`) deletes the Recall bot only if we own it, it hasn't joined, and no other live stand-in needs it. Gated by `PRISM_STANDIN_SCHEDULE` (default ON). **A3 (delivery at join):** on `in_call_recording` (webhook + `/bot-status` fallback, both idempotent via `_standin_delivered` guard + a conditional `pending→delivered` DB claim), `recall_routes.deliver_standins_for_bot()` posts a consolidated chat message of all pending stand-ins for that meeting URL, records it into the transcript (`_record_bot_line`), and stashes them on `bot_store[bot_id]["standin_updates"]` (surfaced in the `/live/{token}` payload → live-share brief card in `LiveMeetingView`). Runs for ANY bot reaching the room (so a teammate's regular bot delivers dedup'd stand-ins too); a scheduled stand-in bot also fires `_send_bot_intro` on join. **Spoken on request:** `_STANDIN_QUERY_RE` in `_process_command` ("any updates from people who couldn't make it") reads `standin_updates` aloud (deterministic, no LLM), only when such updates exist. **A4 (profile + section):** a **"Stand-in" sidebar nav item** (below Knowledge, `activeView==='standin'`, `ProxyProfile.jsx`) where you view/edit your `proxy_profiles` (role/focus + standing notes) and see/cancel your active + past stand-ins (`GET /proxy/profile`, `PUT /proxy/profile`, `GET /proxy/representations`). **Enrichment-on-approve:** `_enrich_profile` (background task fired from `approve`) distils durable facts from the conversation + approved update and merges them into `standing_notes`, so the next draft starts smarter. **Double-bot guard:** `join_meeting` also dedups against `scheduled`-status bots (`_find_existing_bot_for_standin(..., statuses=("scheduled",))`) so auto-join (or any join) attaches to a stand-in bot instead of double-booking. **A5 (follow-up brief — close the loop, Jul 2026):** the stand-in used to be one-way (deliver your message INTO the meeting, then silence). Now, after the meeting is analysed, `proxy_routes.generate_standin_followups(bot_id, meeting_id, result, transcript)` — fired best-effort + non-blocking from `recall_routes._persist_bot_meeting` after `save_meeting` — briefs each absent author this bot delivered for (`delivered_bot_id==bot_id`, status `delivered`). `_build_followup_brief` LLM-writes a short personalized recap (via `_llm_reply`, grounded in summary/decisions/transcript + the rep's relayed `approved_body`): what happened that affects you · answers to what you asked · action items now yours (`_followup_action_items_for` fuzzy-matches owner) · what they need from you. Stamped on the rep (`followup_brief`/`followup_meeting_id`, migration #23) and **emailed** best-effort to `author_email` via the author's own Gmail (`_email_followup_brief`; they own the stand-in bot → the recap lands in their inbox; no-op without Gmail scope, sets `followup_sent_at` on send). Idempotent per rep. UI: `ProxyProfile.jsx` past stand-ins show a "Your brief from this meeting" expander (+ "· emailed" + Open-the-full-meeting link).

**Stand-in hardening + extensions (Jun 22-23 2026, on `main`):**
- **Per-workspace profiles + consent-to-borrow** (migrations #21): `proxy_profiles` is keyed by `(user_id, _ws_key(workspace_id))` so a team stand-in never bleeds personal context (the bug that started this: a workspace draft leaned on the global profile and leaked personal facts). `_load_profile`/`_enrich_profile`/`GET,PUT /proxy/profile` all take `workspace_id`. When a scope is thin (`_scope_is_thin` = <2 work items AND no profile notes), the composer offers **"Pull from" chips** (`_borrow_options` = other workspaces + Personal); a pick widens the gather (`_gather_my_items`/`_gather_my_digest` accept `borrow_scopes`; `_fetch_meetings_for_scopes` unions+dedups) and is persisted on the rep's `borrow_scopes` so it sticks. The resume path re-offers chips (was a dead-end). `_profile_context_multi` merges profile notes across the chosen scopes.
- **Default stand-in** (migration #22, `proxy_profiles.default_standin`): the old "preview" card → **"Your default stand-in"** (`ProxyProfile.jsx`): generate/edit/SAVE a per-space fallback (`PUT /proxy/default-standin` writes only that field). `create_representation` SEEDS the draft with it when the scope is thin (priority over the borrow-ask). `POST /proxy/preview` returns `grounded:false` when thin → UI shows a nudge, not the model asking a question. **Deferred:** true auto-deliver-on-absence (needs opt-in + absence detection).
- **Email FROM the owner's POV:** Tier-2 `email_drafter` runs context-only (no transcript), so `analysis_service._tier1_barrier` parses the `[Meeting owner: NAME]` header and threads `owner_name` into the Tier-2 context; the prompt writes FROM the owner, treats Prism/persona lines as the owner's words, never signs as the assistant. `owner_name` is resolved durably (`recall_routes._resolve_owner_name` from the rep) so a restart that wiped `bot_store` doesn't lose it.
- **Headless self-persistence:** a scheduled stand-in has no browser to `POST /meetings`, so `recall_routes._persist_standin_meeting(bot_id)` auto-promotes its analysis into `meetings` (fan-out + indexing via `save_meeting`, idempotent on `recall_bot_id`). `recover_active_bots()` (main.py lifespan) re-spawns lifecycle pollers on boot (bounded to `meeting_bots` created <6h) so analysis runs after a restart.
- **One bot speaker in analysis:** the stand-in delivery recorded under `DEFAULT_BOT_NAME` while replies use the persona name → the bot was analysed as two speakers. `_normalize_bot_speaker` + `_resolve_bot_persona_name` collapse all bot-attributed transcript lines to one name before analysis.

**Live-bot fixes (Jun 22-23, `realtime_routes.py`):** (1) **No self-feedback loop** — solo free-flow skips the bot's OWN transcribed TTS (`_looks_like_bot_participant(speaker)` guard on both the legacy and accumulator solo paths), else the bot replied to itself endlessly. (2) **Human in-meeting CHAT is recorded into the transcript** (`_record_human_chat_line`) — Recall transcribes audio only, so chat-driven meetings used to analyse to a one-sided monologue. (3) **Solo free-flow applies to typed chat too** — a chat ask in a 1-on-1 (e.g. "email a summary to …") no longer needs a wake word. (4) **Owner email injection** — the live bot is told the owner's real email (`_owner_email_for_bot` → `recall_routes.resolve_owner_email`, lazy+memoized) in the cached system prefix so "email the owner" uses it instead of inventing one; `tools/gmail.py gmail_send` rejects placeholder domains. (5) **Speak short, chat full** (`_spoken_condense`) — each spoken sentence is paced by its real playback duration (so audio doesn't overlap), so a long reply read aloud stalls every queued command behind it; the SPOKEN copy is now capped (list/outline → lead-in + "full breakdown in the chat"; long → first ~3 sentences + "rest in the chat") while the FULL reply still goes to chat. (6) `_fetch_transcript(attempts=2)` short-circuit when a usable live transcript already exists (was waiting ~10 min for Recall audio).
